# Audit, 2026-11: security, performance, honesty

Scope: the whole repository, read-only, plus one run of the app against a real gateway. Every item marked
**confirmed** was re-read in the source by whoever wrote this file; items marked **reported** come from an automated
pass and were not reproduced.

## Fixed in this branch

| # | Where | What was wrong |
| --- | --- | --- |
| 1 | `AndroidManifest.xml:126`, `GatewayUrl.isExposed`, `ConnectScreen.kt` | The app allowed cleartext **and** let you sign in to a public `http://` address with only a red line for a warning. Through a reverse tunnel that is a public address, so the password and every message crossed LTE in the clear. Sign-in is now refused for a public non-`https` address. **Confirmed.** |
| 2 | `GatewayProbe.kt:62` → `ConnectionCheck.kt` | A proxy's `502/503/504` was reported as "this is not a Hermes dashboard, check port 9119". With a tunnel, a live proxy and a dead tunnel is *the* common failure, and the advice pointed at the wrong machine. Now a separate `ProxyFailed` result that names the tunnel and the dashboard. **Confirmed** (new test: `proxyUpstreamErrorIsNotAWrongPort`). |
| 3 | `ChatScreen.kt:2145` | The same `502` produced `Waiting for network…` in the chat, blaming the phone's connection. Now `Gateway down · retrying…`; `ApiResult.Unavailable` carries `fromServer` so the reason is distinguishable from a real network failure. **Confirmed** (test: `theLinkLineSaysWhyTheChatIsOffline`). |
| 4 | `ConnectViewModel.kt:130` | Typing while a probe was running did not cancel it, so a 15-second probe of the *old* text answered under the *new* text, and "Continue" could sign in to the old host. The probe is now cancelled on every edit. **Confirmed** by reading the guard condition. |
| 5 | `HttpClientFactory.kt:45` / `RpcTransport.kt` | `install(WebSockets)` had no frame limit: a gateway — or anything that answers in its place — could send one enormous frame and be killed by the OS. **The obvious fix is a trap**: `install(WebSockets) { maxFrameSize = … }` makes the OkHttp engine throw `Max frame size switch is not supported in OkHttp engine` on *every* upgrade, so the socket dies before the first frame and the app cannot connect at all — measured, not theorised, over `adb reverse` and over the HTTPS proxy alike. The bound is checked per inbound frame in `KtorWebSocketTransport` instead (limit 8 MiB, close 1009 plus `TransportClosedException`), covered by `FrameBoundTest`. Note the residual gap: OkHttp assembles a frame before we see it, so the real backstop for a hostile peer is the server's own limit, not this check. **Fixed.** |
| 6 | `AndroidManifest.xml:437` | `HeraldRecognitionService` was exported with no `android:permission`, while the identical service in `wearApp` is guarded by `BIND_RECOGNITION_SERVICE`. Any app could bind to it. Permission added. **Confirmed.** |

## Open, not fixed here

Ordered by what can actually hurt the owner of a self-hosted gateway.

1. **Wear relay accepts commands from any app on the watch** (`WearBridgeService.kt:49-56`, comment at
   `AndroidManifest.xml:359-372` claims the opposite). `relay.ask(node, …)` runs a full agent turn with the user's
   session; the Data Layer routes by path, not by sender, and offers no signature to check. **Confirmed by code.**
   Fixing this means an app-level MAC shared once over the phone screen — a protocol change, not a patch.
2. **An access token is handed to plugin WebViews as a cookie** and flushed to disk (`PluginWebView.android.kt:121-127`,
   `WebCookieJar.kt:71-77`); `allowContentAccess` is left on. An XSS in any plugin page yields API access as the user;
   a kill before `onDispose` leaves the token in `app_webview/Cookies`. **Reported**, plausible on reading.
3. **Update flow has no integrity check**: the banner opens `browser_download_url` in a browser, and any link ending
   in `.apk` in an agent's reply goes straight to the installer (`UpdateBanner.kt:130`, `InAppBrowser.kt:52`). Android's
   signature check still blocks a foreign signer; phishing and MITM substitution remain. **Reported.**
4. **Streaming is O(n²) and recomposes every visible row** (`ChatReducer.kt:197` `it.text + chunk`;
   `ChatScreen.kt:1888` `partners` rebuilt on every token; `MarkdownText.kt:162` runs full bidi analysis on every
   token). This is the "it lags while the agent types" report. **Reported**; the two `ChatScreen` call sites are
   visible in source, the frame cost was not measured.
5. **History has no memory cap in RAM** (`ChatSession.kt:119` `rows`): up to 50 pages × 500 rows of raw tool output,
   while the on-disk cache caps at 200 rows / 1 MB. Long chats grow the heap without bound. **Reported.**
6. **No baseline profile**, and 11 singletons are constructed synchronously in `Application.onCreate`
   (`HermesApplication.kt:36-58`) — cold start is entirely JIT. **Reported.**
7. **`PushStore` keeps ntfy topics in plaintext** (`PushStore.kt:37`) — metadata only: when and how much, plus the
   ability to spam a reply topic. **Reported.**
8. **Offline cache hides only the payload** (`OfflineDatabase.kt:17-46`): gateway address, profile and session ids
   are in the clear, so a copy of the file reveals who talked to which host. **Reported.**
9. **`MediaApi.remote()` fetches any host the reply names, with no private-address filter** (`MediaApi.kt:128`),
   unlike link previews. Tap-gated SSRF into the local network from the phone. **Reported.**
10. **No localization**: ~1200 hardcoded English strings, no `values-ru`. **Reported.**

## Checked and found sound

Secrets at rest (`EncryptedKeyValueStore`: AES-GCM, key in AndroidKeyStore, fresh IV); `allowBackup="false"` with
exhaustive `data_extraction_rules`; no `trustAll`, no custom `HostnameVerifier`, no empty `checkServerTrusted` anywhere
in the tree; agent-generated widget HTML is inside a sandboxed iframe with `default-src none` and network loads blocked;
no `addJavascriptInterface` in the project; push payloads are signed and verified *before* decryption, with the topic
and direction bound into the AAD; the ws ticket travels in `Sec-WebSocket-Protocol`, not the URL; no request bodies or
tokens are logged.

## Not audited

Dependency CVEs (no lockfile scan), the desktop and Wear apps beyond the items above, and the gateway itself — the
client is only as trustworthy as the `hermes dashboard` it connects to.
